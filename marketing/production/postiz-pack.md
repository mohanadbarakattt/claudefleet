# ClaudeFleet — Postiz Scheduling Pack (30-day calendar → drafts)

Turns `marketing/calendar/week-1.md`…`week-4.md` into Postiz drafts. Nothing in
this pack publishes anything. Every path ends at a draft a human opens, reads,
and releases — which is the same rule the product itself sells (`week-3.md`,
Day 18, slide 6: *"the plan goes to Postiz. It stops there and waits for you to
approve. Nothing publishes itself."*). A pack that auto-published would
contradict the thing it's marketing.

## State of this machine, verified 2026-07-25

| Check | Command run | Result |
|---|---|---|
| CLI installed | `which postiz` | `postiz not found` |
| API key exported | `printenv POSTIZ_API_KEY` | unset |
| Global npm packages | `npm ls -g --depth=0` | no `postiz` entry |

So **everything below starts from zero**. Section 1 is not optional boilerplate;
it is the current state of the box.

Two more constraints that shape this pack, stated plainly rather than worked around:

- **Higgsfield credits are low, and the Higgsfield MCP API was erroring at time
  of writing.** Video assets are generated by pasting prompts into the
  higgsfield.ai web app by hand and saving the result into `assets/`. The batch
  script therefore checks that a local file exists and skips the day if it
  doesn't — it cannot fetch or generate anything. See "Credit triage" below for
  which days you can ship without spending a credit.
- **The 24 clips in `marketing/generated/clips/` are not reusable here.** Their
  `manifest.json` maps them to the retired v2 catalog (CTA keywords
  `STACK`/`VAULT`/`OS`/`FULL`). The current catalog is two machines with
  `CONTENT`/`PRODUCT`/`BOTH`/`START`. Treat that folder as archive, not inventory.

## 1. Setup

### 1.1 Install

```bash
npm install -g postiz
postiz --help          # proves the binary resolves
```

### 1.2 API key — where to keep it so it never lands in a committed file

Do **not** put the key in any file inside `claude-goods/`, and do not paste it
into a script in this directory. Two options, both outside the repo:

**Option A — a mode-600 env file in your config dir (simple):**

```bash
mkdir -p ~/.config/claudefleet
printf 'POSTIZ_API_KEY=%s\n' 'PASTE_KEY_HERE' > ~/.config/claudefleet/postiz.env
chmod 600 ~/.config/claudefleet/postiz.env

# per shell, before using the CLI:
set -a; . ~/.config/claudefleet/postiz.env; set +a
```

**Option B — macOS Keychain (stronger; nothing readable on disk):**

```bash
# one time — prompts for the value, does not echo it into shell history
security add-generic-password -a "$USER" -s postiz_api_key -w

# per shell:
export POSTIZ_API_KEY="$(security find-generic-password -a "$USER" -s postiz_api_key -w)"
```

Either way, add a belt-and-braces ignore so a future `git init` here can't catch it:

```bash
printf '.env\n.env.*\n*.env\n.postiz-ledger.tsv\nassets/\n' >> /Users/mohanadbarakat/projects/claude-goods/.gitignore
```

`POSTIZ_API_URL` only needs setting if you self-host Postiz; leave it unset for
the hosted service.

### 1.3 Discover your integration IDs

Integration IDs are per-account and cannot be known in advance. There are no
real IDs anywhere in this pack — every one is a `[BRACKETED]` placeholder you
replace with output from your own account.

```bash
# human-readable: which channels are actually connected
postiz integrations:list | jq -r '.[] | "\(.id)\t\(.identifier)\t\(.name)"'

# extract one ID into a variable
IG_ID=$(postiz integrations:list | jq -r '.[] | select(.identifier=="instagram") | .id')
echo "$IG_ID"
```

If you have two accounts on the same platform connected, that `select` returns
**two** IDs and the variable silently becomes multi-line. Check `.name` first
and disambiguate:

```bash
postiz integrations:list | jq -r '.[] | select(.identifier=="instagram") | "\(.id)  \(.name)"'
IG_ID=$(postiz integrations:list | jq -r '.[] | select(.identifier=="instagram" and .name=="[YOUR_CHANNEL_NAME]") | .id')
```

### 1.4 Verification — prove the CLI is talking to *your* account

Installation proves nothing about auth. This does:

```bash
postiz integrations:list | jq -e 'length > 0' >/dev/null \
  && postiz integrations:list | jq -r '"OK — \(length) integration(s): \([.[].name] | join(", "))"' \
  || echo "FAIL — key missing, wrong, or no channels connected"
```

A non-empty array whose `.name` values you recognise is the proof. An empty
array means the key authenticated against an account with no channels — a
different problem from a bad key, and worth telling apart before you debug the
wrong thing.

Second verification, before you trust any scheduled date (see §5, timezones):
create **one** throwaway draft, open the Postiz calendar UI, confirm it shows
the local time you intended, then delete it.

```bash
postiz posts:create -c "timezone test, delete me" -s "[ISO_DATETIME]" -t draft -i "$IG_ID"
postiz posts:list                 # find its id
postiz posts:delete [POST_ID]
```

## 2. The 30-day schedule

### 2.1 The one variable

The calendar is written as relative Days 1–30 with no dates. Define Day 1 once:

```bash
START_DATE="[YYYY-MM-DD]"     # Day 1
```

Every other day is `START_DATE + (N-1) days`. Day 7 is `START_DATE + 6`, Day 30
is `START_DATE + 29`. The batch script in §4 does this arithmetic and
self-checks it before running.

### 2.2 Slots — read this before you trust the times in the table

**The calendar states no posting times. The slots below are an arbitrary,
consistent default, not a proven best time, and no claim is made that they
perform well.** Their only virtue is that they are the same every day, which
makes the month a controlled variable you can later measure against.

Three timing facts *are* carried by the calendar itself, and those are real:

1. **One post per day, 30 consecutive days.** Not a preference — it's the shape
   of the file.
2. **Story days need a same-day gap and a human in between.** `week-1.md` Day 6
   frame 2 is *"after a few hours, screenshot the live poll results."* Frame 2's
   content does not exist until frame 1 has been live for hours, so it cannot be
   pre-scheduled with content at all. That is why story frame 1 sits at 09:00 —
   early enough that "a few hours later" is still daytime — rather than in the
   evening slot. Same structure on Days 12 and 20.
3. **Some days depend on assets earlier days produce.** Day 7 needs the week's
   real DMs and comments; Day 20 needs real poll results; Day 30 replays one
   second of Day 7. Those assets cannot exist before their source day has run.

Replace the default slot with your own numbers after ~2 weeks of real data:

```bash
postiz analytics:platform "$IG_ID" -d 30
```

Until that returns data from your own account, any specific time in this
document is a guess wearing a table cell.

### 2.3 Asset naming convention

The batch script looks for these exact paths, relative to wherever you run it:

- `assets/day-NN.mp4` — video reels
- `assets/day-NN-slide-N.png` — carousel slides, in swipe order
- `assets/day-NN-frame-N.png` — story frames

All on-screen copy (text cards, stage labels, "THIS FEELS ILLEGAL TO KNOW",
stopwatch overlays) is added in the edit. No video-model prompt asks for
rendered words — Kling warped text on this project once already and two clips
had to be regenerated (`generated/manifest.json`, reel5-scene3).

### 2.5 Credit triage

Of 30 days, only **five** hard-require a Higgsfield render: **1, 10, 14, 19, 23**
— the same five covered by `higgsfield-calendar-prompts.md`, which carries the
paste-ready prompts and its own protected/droppable ordering. Day 21's cutaway is
marked optional in `week-3.md` itself. Screen-record days are shot-listed in
`screen-record-shotlist.md`. Everything else is screen-record, filmed, or static
design — zero credits.

Spend in this order if credits are short:

1. **Day 1** — it's the first impression of the whole month.
2. **Day 19** — carries the BOTH pivot, first time the two machines are framed
   as one engine.
3. **Day 23** — the "agent employees" concept has no screen-record equivalent.
4. **Days 10 and 14** — Ava segments. Render one Ava source and reuse it across
   10, 14 and 16 rather than rendering three.

**Droppable / replaceable without breaking the arc:**

- **Day 21's cutaway** — drop it. Cut straight into the real recording; the
  calendar already permits this.
- **Day 1** can fall back to a screen-record of the real folder opening on the
  desktop. It loses the pattern-interrupt punch but keeps the day.
- **Days 10, 14, 16** can run as Operator voiceover over screen-record if Ava
  can't be rendered at all. The compliance framing (guide/narrator, never
  claiming a personal result) survives the swap; keep it intact.
- **Day 19** can fall back to the Day 9/13/18 carousel template as a static
  two-pipeline comparison.

Do not "save credits" by faking a screen-record. Every proof day in this
calendar is load-bearing against the scam objection the account spends Day 14
and Day 30 answering directly.

## 3. Ready-to-run commands (one per post shape in this calendar)

Three shapes actually occur: **video reel** (24 days), **static carousel**
(Days 9, 13, 18), **story-style** (Days 6, 12, 20).

**The gotcha that will bite you first:** media must be uploaded to Postiz and
the returned `.path` used in `-m`. Instagram, TikTok and YouTube reject external
URLs — a link to your own S3 bucket or a public Drive file will fail. Upload
first, always.

Also: dates are **required** on every `posts:create` and must be ISO 8601.
There is no "post whenever" mode.

### 3.1 Video reel — Day 2

```bash
DAY_ISO="[START_DATE_PLUS_1]T18:00:00[UTC_OFFSET]"

MEDIA=$(postiz upload assets/day-02.mp4 | jq -r '.path')
[ -n "$MEDIA" ] && [ "$MEDIA" != "null" ] || { echo "upload failed"; exit 1; }

postiz posts:create \
  -c "No mockups, no \"imagine this.\" Here's the actual folder, the actual slash command, the actual script it wrote — recorded live. This is the Autopilot Content Machine. \$99, and heads up: that's the system, not the Claude/Higgsfield/Postiz subscriptions it runs on. Comment CONTENT and it's in your DMs." \
  -m "$MEDIA" \
  -s "$DAY_ISO" \
  -t draft \
  --settings '{"post_type":"post"}' \
  -i "[INSTAGRAM_INTEGRATION_ID]"
```

Note the escapes: `\"` for the caption's inner quotes and `\$99` so the shell
doesn't try to expand `$99`. Both appear in real captions in this calendar.

`post_type` — check what your Instagram integration actually accepts before
assuming a value exists for reels:

```bash
postiz integrations:settings "[INSTAGRAM_INTEGRATION_ID]" | jq '.output'
```

Do not guess `"reel"`. Read the schema.

### 3.2 Static carousel — Day 9 (6 slides)

Upload every slide, keep swipe order, join the paths with commas:

```bash
DAY_ISO="[START_DATE_PLUS_8]T18:00:00[UTC_OFFSET]"

PATHS=""
for i in 1 2 3 4 5 6; do
  P=$(postiz upload "assets/day-09-slide-${i}.png" | jq -r '.path')
  [ -n "$P" ] && [ "$P" != "null" ] || { echo "slide $i upload failed"; exit 1; }
  PATHS="${PATHS:+$PATHS,}$P"
done

postiz posts:create \
  -c "Swipe through the actual 5 stages — this is the whole pipeline, not a teaser. Screenshot slide 3 if scripting is where you always get stuck. If you want the other 14 prompts already written behind this pipeline, comment CONTENT and I'll DM the link." \
  -m "$PATHS" \
  -s "$DAY_ISO" \
  -t draft \
  --settings '{"post_type":"post"}' \
  -i "[INSTAGRAM_INTEGRATION_ID]"
```

The loop appends in numeric order, so slide order is the array order. Verify it
in the draft preview before releasing — a scrambled carousel is invisible in the
CLI output and obvious to every viewer.

### 3.3 Story-style — Day 6, frame 1 only

**Read this before scheduling any story day.** Days 6, 12 and 20 are built on
Instagram's *native* poll, question and slider stickers, and the calendar
requires the results be real (`week-1.md` Day 6: *"faking poll numbers would
break the no-fake-proof rule"*; `week-3.md` Day 20: *"never invent or mock up a
result split"*). Nothing in the Postiz CLI surface exposes those native
stickers — it schedules a media file. Which means:

- **Frame 1** can be scheduled as a background image, but the sticker still has
  to be placed in the Instagram app. In practice these three days are
  manual-post days, and the value of putting them in Postiz is that they appear
  on the calendar as a reminder rather than being forgotten.
- **Frames 2+ cannot be pre-scheduled at all.** Their content is a screenshot of
  results that don't exist yet.

Confirm against your own integration before deciding — do not take the above as
final without checking:

```bash
postiz integrations:settings "[INSTAGRAM_INTEGRATION_ID]" | jq '.output'
```

Frame 1 as a scheduled draft, if you want the reminder on the calendar:

```bash
DAY_ISO="[START_DATE_PLUS_5]T09:00:00[UTC_OFFSET]"

STORY=$(postiz upload assets/day-06-frame-1.png | jq -r '.path')

postiz posts:create \
  -c "" \
  -m "$STORY" \
  -s "$DAY_ISO" \
  -t draft \
  --settings '{"post_type":"story"}' \
  -i "[INSTAGRAM_INTEGRATION_ID]"
```

### 3.4 Multi-platform, from the JSON file

```bash
postiz posts:create --json postiz-batch.example.json -t draft
```

See `postiz-batch.example.json` (Day 27, BOTH) for the format. Its header keys
flag which fields we could not verify against a documented reference — read
them before trusting the file.

## 4. Batch script — schedule one week as drafts

Safe to re-run. Defaults to a dry run. Creates drafts only.

### 4.1 Before the first run: check what's already there

`posts:create` always creates. It has no upsert. So look before you leap:

```bash
postiz posts:list --startDate "[START_DATE]T00:00:00Z" --endDate "[START_DATE_PLUS_6]T23:59:59Z"
```

Inspect one record's actual shape before writing any automation against it —
field names vary between CLI versions and this pack does not guess them:

```bash
postiz posts:list | jq '.[0]'
```

The script's own re-run safety comes from a local ledger it writes
(`.postiz-ledger.tsv`, one line per scheduled day). If you delete a draft in the
Postiz UI, delete its ledger line too, or the script will think it still exists.

### 4.2 `schedule-week1.sh`

```bash
#!/usr/bin/env bash
# Creates Days 1-7 of the ClaudeFleet calendar as Postiz DRAFTS. Publishes nothing.
# Re-runnable: days already in the ledger are skipped.
set -euo pipefail

# ---- operator config -------------------------------------------------------
START_DATE="[YYYY-MM-DD]"              # Day 1
FEED_SLOT="18:00:00"                   # untested default — see section 2.2
STORY_SLOT="09:00:00"
UTC_OFFSET="[+00:00]"                  # your local offset, e.g. +02:00
IG_ID="[INSTAGRAM_INTEGRATION_ID]"     # from: postiz integrations:list
ASSET_DIR="./assets"
LEDGER="./.postiz-ledger.tsv"
DRY_RUN="${DRY_RUN:-1}"                # 1 = print only. DRY_RUN=0 to create drafts.
# ---------------------------------------------------------------------------

command -v postiz >/dev/null || { echo "postiz not installed: npm install -g postiz"; exit 1; }
: "${POSTIZ_API_KEY:?POSTIZ_API_KEY not exported — see section 1.2}"
command -v jq >/dev/null || { echo "jq required"; exit 1; }

day_date() {   # $1 = day number -> YYYY-MM-DD, START_DATE + (N-1) days
  local n=$(( $1 - 1 ))
  date -j -v+"${n}"d -f "%Y-%m-%d" "$START_DATE" +%Y-%m-%d 2>/dev/null \
    || date -d "$START_DATE + $n days" +%Y-%m-%d
}

self_check() {  # fails loudly if date math is wrong on this shell (BSD vs GNU date)
  local saved="$START_DATE" ok=1
  START_DATE="2026-08-03"
  [ "$(day_date 1)" = "2026-08-03" ] || ok=0
  [ "$(day_date 7)" = "2026-08-09" ] || ok=0
  START_DATE="2026-08-28"
  [ "$(day_date 7)" = "2026-09-03" ] || ok=0    # month rollover
  START_DATE="$saved"
  [ "$ok" = 1 ] || { echo "date math broken on this shell — fix day_date() before running"; exit 1; }
}
self_check

[[ "$START_DATE" =~ ^[0-9]{4}-[0-9]{2}-[0-9]{2}$ ]] \
  || { echo "set START_DATE to a real YYYY-MM-DD"; exit 1; }

# All three placeholders must be replaced, not just START_DATE. An unreplaced
# UTC_OFFSET emits 2026-08-03T18:00:00[+00:00], which is not ISO 8601, and an
# unreplaced IG_ID posts at a channel that does not exist.
[[ "$UTC_OFFSET" =~ ^[+-][0-9]{2}:[0-9]{2}$ ]] \
  || { echo "set UTC_OFFSET to a real offset like +02:00 (yours is still a placeholder)"; exit 1; }
case "$IG_ID" in
  ""|\[*) echo "set IG_ID from: postiz integrations:list  (yours is still a placeholder)"; exit 1 ;;
esac

# Captions verbatim from marketing/calendar/week-1.md. Indexed by day number.
# Day 6 is deliberately empty: story day, native stickers, no feed caption.
CAPTION=()
CAPTION[1]="Everyone's downloading more apps. I deleted mine and gave Claude a five-stage content pipeline instead. Screen-recording the actual setup this week — no hype, just the folder. Comment CONTENT and I'll send it over."
CAPTION[2]="No mockups, no \"imagine this.\" Here's the actual folder, the actual slash command, the actual script it wrote — recorded live. This is the Autopilot Content Machine. \$99, and heads up: that's the system, not the Claude/Higgsfield/Postiz subscriptions it runs on. Comment CONTENT and it's in your DMs."
CAPTION[3]="Nobody's going to jail over this, it just feels like a cheat code because most people never open the folder. 17 build prompts, 5 agent employees, one pipeline: idea in, scheduled post out. Comment CONTENT for the link."
CAPTION[4]="You don't need a hundred AI prompts saved. You need a pipeline that actually finishes. Here are 3 of the 17 in the Autopilot Content Machine. Comment CONTENT and I'll send the rest."
CAPTION[5]="Timed it so you don't have to take my word for it: full install, under 2 minutes, on screen the whole time. This is the Autopilot Content Machine — \$99, plus your own Claude/Higgsfield/Postiz subscriptions running underneath it. Comment CONTENT for the link."
CAPTION[6]=""
CAPTION[7]="One week of showing the actual folder instead of talking about it. This week I ran the real install end to end — found 3 real bugs, fixed all 3, all recorded. That's what \"it works\" means here: a receipt, not a claim. Autopilot Content Machine is \$99 (Claude/Higgsfield/Postiz subscriptions not included — worth saying plainly). Comment CONTENT and I'll send it."

[ "$DRY_RUN" = 1 ] && echo "== DRY RUN (set DRY_RUN=0 to create drafts) =="

for d in 1 2 3 4 5 6 7; do
  printf -v dd "%02d" "$d"

  if [ -f "$LEDGER" ] && awk -F'\t' -v d="$d" '$1==d{f=1} END{exit !f}' "$LEDGER"; then
    echo "day $dd: already in $LEDGER — skipping"
    continue
  fi

  if [ -z "${CAPTION[$d]:-}" ]; then
    echo "day $dd: MANUAL — native IG poll/question stickers and real results; post from the app at ${STORY_SLOT%%:*}:00 (see calendar/week-1.md Day $d)"
    continue
  fi

  ISO="$(day_date "$d")T${FEED_SLOT}${UTC_OFFSET}"
  ASSET="$ASSET_DIR/day-${dd}.mp4"

  if [ ! -f "$ASSET" ]; then
    echo "day $dd: missing $ASSET — skipping (generate or record it first)"
    continue
  fi

  if [ "$DRY_RUN" = 1 ]; then
    echo "day $dd: would upload $ASSET and create a DRAFT for $ISO"
    continue
  fi

  MEDIA="$(postiz upload "$ASSET" | jq -r '.path')"
  if [ -z "$MEDIA" ] || [ "$MEDIA" = "null" ]; then
    echo "day $dd: upload failed — skipping, ledger not written"
    continue
  fi

  # NOTE: a bare OUT="$(cmd)" assignment takes the command's exit status, so under
  # `set -e` the FIRST failed create kills the whole run — and the error text is
  # trapped inside $OUT, never printed. Guard it so the day is reported and the
  # loop carries on to the rest of the week.
  if ! OUT="$(postiz posts:create \
        -c "${CAPTION[$d]}" \
        -m "$MEDIA" \
        -s "$ISO" \
        -t draft \
        --settings '{"post_type":"post"}' \
        -i "$IG_ID" 2>&1)"; then
    echo "day $dd: posts:create FAILED — ledger not written"
    printf '%s\n' "$OUT" | sed 's/^/    /'
    continue
  fi

  printf '%s\t%s\t%s\n' "$d" "$ISO" "$(printf '%s' "$OUT" | tr '\n' ' ')" >> "$LEDGER"
  echo "day $dd: draft created for $ISO"
done

echo
echo "Drafts only. Nothing is scheduled to publish."
echo "Next: open the Postiz calendar, review every draft, release the ones you approve."
```

### 4.3 Extending to Weeks 2–4

Same loop; three changes. Swap `CAPTION[…]` for the captions in `week-2.md`,
`week-3.md`, `week-4.md`; change the day list (`8 9 10 …`); and branch on shape —
carousel days build a comma-joined `-m` list from `day-NN-slide-*.png` per §3.2,
story days print the manual reminder per §3.3. Days 9, 13, 18 are carousels;
Days 12 and 20 are stories; everything else is the video path already written.

Day 30's caption ends *"No link today"* — it carries the `START` keyword but no
product link. Don't let a template add one.

### 4.4 Releasing a draft

The script stops at drafts on purpose. Review is a human step:

1. Open the Postiz calendar UI.
2. Read each draft against its day in `calendar/week-N.md` — caption, asset,
   CTA keyword.
3. Confirm the date renders as the local time you intended.
4. Release the ones you approve, one at a time.

Confirm the exact set of values `-t` accepts on your installed version before
scripting anything past `draft`:

```bash
postiz posts:create --help
```

Only `-t draft` is documented in the reference this pack was built from. The
rest is your CLI's business, not ours to guess.

## 5. Troubleshooting

**`POSTIZ_API_KEY` unset.** Every command fails at auth. The env var does not
survive a new shell — Option A/B in §1.2 must be re-sourced per terminal, or
added to your shell profile. Diagnose with the §1.4 verification, not by
staring at the error.

**Stale integration ID.** IDs change when a channel is disconnected and
reconnected. Symptom: commands that worked last week now fail on a channel you
can see in the UI. Fix: re-run `postiz integrations:list` and re-extract. Never
hardcode an ID into a script that outlives a reconnection — read it into a
variable at the top of the run.

**External media URL rejected.** The single most common failure. Instagram,
TikTok and YouTube only accept verified URLs. Passing a public link — S3, Drive,
your own CDN — to `-m` fails. Always `postiz upload <file>` first and use the
returned `.path`:

```bash
MEDIA=$(postiz upload assets/day-02.mp4 | jq -r '.path')
```

Guard for the null case; `jq -r` prints the string `null` on a miss, and `null`
is a perfectly valid-looking argument that fails much later and less clearly.

**Missing release ID after publishing.** Some platforms (TikTok especially)
don't return a post ID at publish time. `analytics:post` then returns
`{"missing": true}` instead of metrics. Resolve it:

```bash
postiz analytics:post [POST_ID]                        # {"missing": true}
postiz posts:missing [POST_ID]                         # lists provider content
postiz posts:connect [POST_ID] --release-id "[CONTENT_ID]"
postiz analytics:post [POST_ID]                        # now returns metrics
```

Match by the cover-image URL in the `posts:missing` output — connecting the
wrong content silently attributes another post's numbers to this one.

**Character limits.** Read them, never assume them. Limits differ per platform
and change:

```bash
MAX=$(postiz integrations:settings "[INTEGRATION_ID]" | jq '.output.maxLength')
CAPTION="[YOUR_CAPTION]"
[ "${#CAPTION}" -le "$MAX" ] || echo "over by $(( ${#CAPTION} - MAX )) chars"
```

This bites hardest on this calendar's longest captions — Days 7, 14, 27 and 30
all run long because they carry the subscription disclosure and the
no-guarantees language. **Trim the hype, never the disclosure.** If a caption
must lose characters, the "$99 doesn't include Claude/Higgsfield/Postiz" line
and the 30-day-refund line stay; the atmosphere goes.

**Dates and timezones.** ISO 8601, required, on every post. This pack emits
`…T18:00:00[UTC_OFFSET]`. If your Postiz rejects the offset form, convert the
slot to UTC and use the `Z` suffix instead. Either way, prove it with the §1.4
throwaway draft before you schedule 30 of them — an off-by-one-timezone month is
tedious to unpick.

**Duplicate posts after a re-run.** `posts:create` has no upsert. Re-running the
script without its ledger creates a second copy of every day. If it happens:
list the window, identify the duplicates, delete by ID.

```bash
postiz posts:list --startDate "[ISO_START]" --endDate "[ISO_END]"
postiz posts:delete [POST_ID]
```

**Shell escaping in captions.** These captions contain `$99`, apostrophes, em
dashes and inner double quotes. In double-quoted shell strings, escape `\$` and
`\"`. A caption that posts as `9` instead of `$99` is a pricing error published
to an audience, not a typo.

**Postiz CLI absent / command not found.** Confirmed absent on this machine
(§0). `npm install -g postiz`, then `postiz --help`. If the binary installs but
doesn't resolve, your global npm bin directory isn't on `PATH` — `npm prefix -g`
(then append `/bin`; note `npm bin -g` was removed in npm v9 and errors on modern npm)
prints where it went.

## 6. What this pack does not do

- It does not publish. Every path ends at a draft.
- It does not generate media. The Higgsfield MCP API was erroring at time of
  writing, so prompts are pasted into the web app by hand and results saved into
  `assets/`. The script checks for files; it cannot create them.
- It does not know your posting times. §2.2's slots are defaults, replaced by
  your own `analytics:platform` data once you have any.
- It does not add Instagram's native stickers. Days 6, 12 and 20 are manual.
- It contains no real integration IDs, channel names, handles or account IDs —
  every one is a placeholder, because they are per-account and cannot be known
  in advance.
